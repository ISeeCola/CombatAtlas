# 每日战斗设计资料巡检

香港时间每日 09:00 增量扫描。任务读取本地工作规范、priority sources、registry、双工作簿和历史，以 canonical URL、平台 ID、标准化标题及讲者/会议去重。每轮先处理最多 3 条尚未处理当前评论版本的“待修改”，再最多新增 3 条“待复核”；重做不占新增额度。

## 每日新增候选字段契约

每日新增不能只写基础元数据。每个 `newCandidates[]` 对象还必须提供以下网页准备字段：

- `summary`：1-3 句中文摘要，只总结当前可复查证据。
- `keyTakeaways`：2-4 条中文数组，写入 Excel 时以单元格内换行保存；不得把推测伪装成演讲结论。
- `readingMinutes`：正整数。优先使用官方时长；只有会议时段可查时使用时段长度，并在审核备注说明估算依据。
- `displayValue`：1-5 的整数，仅为自动化初始建议，维护者可覆盖。
- `featured`：布尔值。自动化新增默认 `false`，精选必须由维护者判断。
- `addedAt`：候选首次写入 Review 当日的香港日期，格式为 `YYYY-MM-DD`；这是未来网页的收录日期，不代表已批准入库。

除上述六个网页准备字段外，每条新增候选还必须提供标题、作者、来源、URL、发布年份、语言、媒介、来源层级和至少一个主题。脚本在打开和修改工作簿前对整批候选、主表/Review/终态重复项与冲突执行校验。任一候选缺字段、结论数量错误、枚举或数值越界、日期或 URL 非法时，整批不写入 Review，并将原始输入保留到本地 `pending/`。每日任务必须先修正该输入再重放，不得通过填充空字符串绕过。

URL 去重只统一协议与域名大小写，移除 fragment、默认端口和非根路径末尾无意义的 `/`；路径与查询字符串大小写必须保留。Review 文件锁位于 `.runtime/locks/`，成功保存后才删除 pending 输入。

来源按三级处理：高质量入口优先查询并作为 canonical；只有高质量入口不存在或不可用时，才使用次级质量入口；低质量网站仅可提供标题、作者或项目名等检索线索，不得写入候选 URL。找不到更可靠入口时跳过，且不占每日新增额度。具体名单以 `priority-sources.md` 和 `curation-config.json` 为准。

自动化最高只能推进至“待复核”，不得设置“已接受”“已入库”或“已拒绝”，也不得批准入库、修改主表、提交 Git、推送 GitHub 或发布网页。无变化保持安静；仅在新增候选、完成/无法完成待修改、链接失效、来源修正、文件锁、失败或需要人工决定时通知。Excel 文件锁定时写入忽略的 `pending/`，下次先幂等重放。

## 定时任务与代码维护边界

- 每日巡检只允许执行仓库中已经提交的脚本。它不得创建、修改、格式化或删除 `scripts/`、`app/`、`tests/`、工作流配置及其他 Git 跟踪文件。
- 巡检可以写入本地 Review 工作簿、`automation/pending/`、`.runtime/` 诊断，以及由 Review 同步生成的本地策展文档；不得修改主表或网页公开数据。
- 若既有脚本出现语法错误、幂等失败、状态机冲突或其他工具缺陷，本轮必须关闭失败：保留可重放输入，在 `.runtime/logs/` 写明阶段、命令和错误，并通知维护者。定时任务不得在运行中热修复代码。
- 工具缺陷进入独立维护流程：人工任务修复代码，运行校验并单独提交/推送。仓库恢复干净后，下一轮巡检再重放 pending。
- Excel 发布安全门继续拒绝任何非文章发布范围的 Git 改动。巡检遵守上述边界后，正常运行不会制造这类改动，也不会阻塞主表直接发布。
- pending 重放必须幂等：评论哈希已处理且状态已推进的记录直接跳过；整批成功保存后删除对应 pending，失败时原文件保持不变。

遇到 GDC 内容时，先寻找高质量的 GDC 官方 YouTube 或其他官方公开视频；视频可得时优先记录视频链接，次级质量的 Vault 作为关联证据。脉脉等低质量来源只能用于追溯原件。“待修改”必须读取“评论”并按评论 SHA-256 幂等更新原记录；成功后转“待复核”，失败则保持“待修改”。“已拒绝”和“重复”均为终态去重集合，不得重新发现或另建记录。
